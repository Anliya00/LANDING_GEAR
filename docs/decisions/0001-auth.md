# 0001 — Authentication and session management

Status: accepted · Date: 2026-10-06

## Context

SFTAD needs four roles (engineer, operator, viewer, admin) across a small
internal user base, on an internal network, behind one FastAPI process and one
Oracle 21c database. Engineers keep the dashboard open for hours. The D1
specification requires the upload source IP to be recorded against each flight.

## Decisions

### Application users in application tables, not Oracle database accounts

Oracle accounts would give password policy and auditing for free, but they
break connection pooling (connections would carry per-user identity), leave the
background worker without an identity of its own, and would require the web
application to issue `CREATE USER` and `GRANT` — DDL from an HTTP request — for
the user administration page.

Oracle is accessed by one low-privilege service account. Identity is the
application's own.

### Server-side sessions, not JWT

JWT's advantage is statelessness across many services. There is one service
here, so the benefit does not apply while the cost does: a JWT cannot be
revoked before it expires, so a disabled account keeps working. A session row
ends access on the next request.

Sliding expiry avoids the refresh-token machinery a short-lived JWT would need
for an interface left open all day. The session row also already holds the
client IP that flight registration must record.

### Opaque token in an httpOnly cookie, SHA-256 stored

The cookie value carries no claims and no structure; the database is the source
of truth. Only the hash is stored, so reading SESSIONS does not yield live
sessions. `httpOnly` keeps it out of reach of injected script;
`SameSite=Strict` means a cross-site request arrives without it, which is what
removes the need for separate CSRF tokens.

`Secure` is configurable because the proof of concept may run over plain HTTP,
where a browser silently drops a Secure cookie and login appears to do nothing.
It must be set to true in production.

### Argon2id for passwords

Current recommendation, single dependency, and the encoded hash carries its own
parameters so cost can be raised later without a schema change. Hashes are
upgraded opportunistically on successful sign-in.

### Role comes from the server, never from the login form

The reference mockup has a role dropdown at sign-in. That lets a viewer select
Administrator. Role is read from USER_ROLES after the password is verified. A
"view as" switcher for genuinely multi-role accounts can live in the user menu
later, where it belongs.

### USER_ROLES as a join table

A role column on USERS would be smaller today and would need migrating the
first time anyone legitimately holds two roles. The join table costs nothing
now.

### Usernames stored and compared lowercased

Otherwise `Joe` and `joe` become two accounts and the UNIQUE constraint does
not prevent it.

### Temporary lockout, generic failure message

Failed attempts increment a counter; crossing the threshold sets
`LOCKED_UNTIL` rather than a permanent lock, so a typo does not need an
administrator. Unknown username and wrong password return the same message and
spend comparable time, so the form cannot be used to enumerate accounts.

### An authentication backend interface

`LocalPasswordBackend` today. If CADC has an LDAP or Active Directory, that
becomes a second implementation and a config switch rather than a rewrite —
and leavers would then be handled by the existing directory process. Worth
asking before the user base grows.

## Deferred

Password reset flow (an administrator resets, for now), sign-in audit log,
rate limiting beyond the per-account lockout, LDAP, multi-role "view as".

## Consequences

Nothing authentication-related is stored in `localStorage`. The frontend
discovers who is signed in by calling `/auth/me` on load, and a 401 from that
call is the ordinary signed-out answer rather than an error.
